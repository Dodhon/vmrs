## Acceptance Test Plan (MVP)

### Scope & Inputs
- Limit acceptance tests to the Neo4j-backed QA layer per `project_context.md`; the chatbot shell is already complete.
- Treat `vendor data/checked/Motors Part Cleanup - Return Data.csv` as the vendor-authoritative ground truth, and `knowledge_graph_output/combined_triple_extraction_and_md_tables_codes.csv` as the exact snapshot loaded into Neo4j.
- Every test must cite the MCP query plus the CSV rows used for verification so stakeholders can trace answers back to their sources.

### Starter Acceptance Tests
1. **Mirror actuator VMRS lookup**
   - *Question*: “What is the VMRS code for a mirror actuator?”
   - *Expected answer*: VMRS `002-010-084`, described as Actuator - Mirror within System `002` (Cab & Sheet Metal) and Assembly `010` (Mirrors).

2. **Radiator grille VMRS lookup**
   - *Question*: “What is the VMRS code for a grille?”
   - *Expected answer*: VMRS `002-001-001`, “Grille - Radiator,” under System `002` (Cab & Sheet Metal) and Assembly `001` (Radiator Grille).

3. **A/C receiver drier VMRS lookup**
   - *Question*: “What is the VMRS code for an A/C receiver dryer?”
   - *Expected answer*: VMRS `001-001-065`, “Receiver - Dehydrator Assembly (Drier),” tied to System `001` (Air Conditioning/Heating) and Assembly `001` (Air Conditioning Assembly - Complete).

4. **Assemblies spanning multiple vehicle systems**
   - *Question*: “Which assemblies span across multiple vehicle systems?”
   - *Expected answer*: Default expectation is “none” (VMRS assemblies are namespaced per system). If any assemblies genuinely appear under multiple system codes, list each `(assembly_name, system_code)` combination explicitly.
